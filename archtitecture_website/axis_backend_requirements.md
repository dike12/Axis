## 1. Architecture Overview

Axis Finance uses a **modular monolith** pattern — a single FastAPI application organized into strict feature modules. Each module owns its own router, models, schemas, and service layer. This allows fast development now while making it straightforward to extract individual modules into separate microservices when moving to multi-user at scale.

### 1.1 Folder Structure

| Path | Purpose |
|---|---|
| `app/` | Application root |
| `app/main.py` | FastAPI app factory, router registration, CORS, startup events |
| `app/core/` | Shared config, database session, auth middleware, dependencies |
| `app/core/config.py` | Environment variables (DB URL, API keys, session secret) |
| `app/core/database.py` | SQLAlchemy async engine + session factory |
| `app/core/auth.py` | Password hashing, JWT session validation |
| `app/modules/` | One folder per feature module |
| `app/modules/transactions/` | Transactions router, models, schemas, service, csv_parser |
| `app/modules/budget/` | Budget planner router, models, schemas, service |
| `app/modules/investments/` | Investments router, models, schemas, service, price_fetcher |
| `app/modules/analysis/` | Analysis router, service (reads from other modules) |
| `app/modules/settings/` | User settings router, models, schemas, service |
| `app/modules/auth/` | Auth router, register/login service |
| `alembic/` | Database migrations |
| `docker-compose.yml` | PostgreSQL + FastAPI services |
| `.env` | Environment variables (never commit to git) |

### 1.2 Module Rules (Enforce These Always)

- Each module **MUST** only import from `app/core/` or its own folder
- Cross-module data access **MUST** go through service layer calls, never direct model imports
- Each module has its own Alembic migration file
- No business logic in routers — routers call services, services call models
- Every module is independently testable in isolation

## 4. Core Business Logic

### 4.1 Income Rollover Rule

> This is the most important piece of business logic in the entire backend. It must be implemented correctly and consistently.

**Rule Definition**

- When a transaction is of type `credit` (income) AND its `date` is >= `income_cutoff_day` (default: 20th) of the month:
  - The backend automatically sets `effective_date` = 1st day of the following month
  - The `is_shifted` flag is set to `TRUE` on that transaction
- If `shift_override = TRUE` on the transaction, skip this logic and use `date` as `effective_date`
- All dashboard metrics, budget planner actuals, and analysis use `effective_date` — **never** `date`
- The Ledger/Transactions table shows the real date with a 'Shifted' badge when `is_shifted = TRUE`

**When Recalculation is Triggered**

- On every new transaction `POST` — calculate `effective_date` before insert
- On transaction `PUT` — recalculate unless `shift_override` is explicitly set
- When user changes `income_cutoff_day` in settings — recalculate **ALL** historical transactions
- When user toggles `shift_late_income` OFF in settings — set `effective_date = date` for all, `is_shifted = FALSE` for all

### 4.2 Budget Actual Computation

The `actual_amount` in `budget_values` is **never** manually set — it is always computed from transactions.

- For **expense** categories: sum of `ABS(amount)` for transactions where `effective_date` falls in that month/year and category matches
- For **income** categories: sum of `amount` for credit transactions where `effective_date` falls in that month/year and category matches
- For **savings** categories: treat as expense (money going out to savings accounts)
- This computation runs on-demand when `GET /budget/values` is called — not stored statically
- Alternatively, update `actual_amount` as a background task whenever a transaction is created/updated/deleted

### 4.3 CSV Import Pipeline

**Step 1 — Parse**

- Accept `multipart/form-data` CSV file upload
- Detect delimiter (comma or semicolon)
- Read headers, return first 5 rows as preview with detected column names
- Return a session token (`import_batch_id`) tied to the parsed data in memory or temp storage

**Step 2 — Map + Categorize**

- User sends column mapping: `{ date_col, description_col, amount_col, type_col? }`
- Backend parses all rows using the mapping
- Auto-categorize each row by matching description against keyword rules:

| Keywords | Category |
|---|---|
| Walmart, Whole Foods, Loblaws, Metro, Sobeys | Food |
| Netflix, Spotify, Disney+, Apple TV | Subscriptions |
| Shell, Esso, Petro-Canada, Gas, Uber, Lyft | Transportation |
| Hydro, Electric, Internet, Rogers, Bell, Telus | Utilities |
| Salary, Payroll, Direct Deposit | Income |
| Amazon, Apple.com, Best Buy | Shopping |
| Pharmacy, Shoppers, Rexall | Health |
| Unmatched | Uncategorized |

- Run duplicate detection: flag rows where `date + amount + description` match an existing transaction
- Return full parsed preview with categories, amounts, types, and duplicate flags

**Step 3 — Confirm Import**

- User confirms, optionally sending category overrides per row
- Backend inserts all non-duplicate rows (or all if user chose to include duplicates)
- Apply rollover logic to each imported transaction
- Return `{ imported: N, skipped: N, import_batch_id }`

### 4.4 Live Investment Prices (Alpha Vantage)

- Price fetcher is a standalone service module: `app/modules/investments/price_fetcher.py`
- On `POST /investments/refresh-prices`, fetch current price for each holding symbol from Alpha Vantage
- Alpha Vantage free tier: **25 API calls/day, 5 calls/minute** — implement rate limiting and request queuing
- For stocks/ETFs: use `GLOBAL_QUOTE` endpoint
- For crypto (BTC, ETH etc.): use `CURRENCY_EXCHANGE_RATE` endpoint
- Store `current_price` and `price_updated_at` on each investment row after fetch
- If fetch fails for a symbol, keep last known price, log the error, do not crash other symbols
- Auto-refresh trigger: on app startup if `price_updated_at` is older than 24 hours

### 4.5 Dashboard Metric Computations

**Runway**

- `runway_months = total_liquid_cash / avg_monthly_spend`
- `total_liquid_cash` = sum of liquid investment values + (total income − total expenses) for last 3 months
- `avg_monthly_spend` = average of last 3 months of total expense (using `effective_date`)

**FI Progress**

- `fi_target = (avg_annual_spend / 0.04)` — the 4% rule
- `avg_annual_spend` = sum of last 12 months of expenses
- If `fi_target_override` is set in `user_settings`, use that instead
- `fi_progress_pct = (total_investment_portfolio_value / fi_target) * 100`
- `fi_projected_year = current_year + (fi_target - portfolio_value) / avg_annual_savings`

**Debt Load**

- `debt_load_pct = (total_monthly_debt_payments / total_monthly_income) * 100`
- Threshold labels: < 20% = Healthy, 20–35% = Moderate, > 35% = High Risk
- Debt payments = transactions in categories tagged as debt (credit card, loan, mortgage)

## 5. Authentication

Auth is implemented as its own module (`app/modules/auth/`) so it can be extracted into a separate service when going multi-user. The current implementation uses email and password authentication. Google OAuth 2.0 will be added later alongside this without replacing it.

### 5.1 Email/Password Auth Flow

- `POST /auth/register` — validate email uniqueness, hash password with bcrypt (cost factor 12), create user row and default `user_settings` row, issue JWT cookie
- `POST /auth/login` — look up user by email, verify password against bcrypt hash, issue JWT cookie; return 401 on any mismatch (never reveal whether email exists)
- Session stored as an **HTTP-only secure cookie** (not localStorage)
- Session token is a signed JWT containing `user_id` and expiry (7 days)

### 5.2 Multi-User Readiness

- Every DB query in every module **MUST** filter by `user_id` from the session
- `user_id` is **never** trusted from the request body — always taken from the validated session
- Adding a second user later requires zero schema changes
- Google OAuth 2.0 can be added alongside email/password later without replacing it — just add new endpoints to the auth module

### 5.3 Required Environment Variables

| Variable | Description |
|---|---|
| `SESSION_SECRET_KEY` | Random 32-byte string for signing session JWTs |
| `DATABASE_URL` | `postgresql+asyncpg://user:pass@localhost:5432/axisfinance` |
| `ALPHA_VANTAGE_API_KEY` | From alphavantage.co free account |
| `CORS_ORIGINS` | `http://localhost:5173` (Vite dev server) |

## 6. Docker Setup

The entire backend runs via Docker Compose. Two services: the FastAPI app and PostgreSQL. The frontend Vite dev server runs separately on the host.

### 6.1 Services

| Service | Image | Port | Purpose |
|---|---|---|---|
| db | postgres:15-alpine | 5432 | Primary PostgreSQL database |
| api | Custom Dockerfile | 3000 | FastAPI application server |

### 6.2 Key Requirements

- PostgreSQL data persisted via a named Docker volume (`axisfinance_pgdata`)
- API container `depends_on` db with health check before starting
- Alembic migrations run automatically on API container startup
- `.env` file mounted into API container — never baked into the image
- Hot reload enabled in development via volume mount of `app/` folder
- CORS configured to allow `http://localhost:5173` (Vite frontend)

## 7. Non-Functional Requirements

### 7.1 Modularity Rules

- Each module folder is self-contained: `router.py`, `models.py`, `schemas.py`, `service.py`
- No circular imports between modules
- Shared utilities go in `app/core/` only
- Each module registers its own `APIRouter`, mounted in `main.py`
- Adding a new feature = adding a new folder in `app/modules/` — nothing else changes

### 7.2 Error Handling

- All endpoints return consistent JSON: `{ data: null, error: { code, message } }` on failure
- HTTP `400` for validation errors (Pydantic), `401` for unauthenticated, `403` for unauthorized, `404` for not found, `500` for server errors
- Never expose raw database errors or stack traces to the client
- Log all 500 errors with full traceback to stdout (Docker captures this)

### 7.3 Data Validation

- All request bodies validated with Pydantic v2 schemas
- Amount fields: must be non-zero numeric, max 12 digits, 2 decimal places
- Date fields: must be valid dates, not in the future for transactions
- Category names: max 100 characters, no special characters
- Symbol fields: uppercase only, max 20 characters

### 7.4 Performance

- All DB queries use async SQLAlchemy sessions (never blocking)
- Budget actual computation: cache result for 60 seconds to avoid recomputing on every request
- Alpha Vantage calls: never block a user-facing request — run as background task
- CSV imports: process in chunks of 500 rows for large files

### 7.5 Testing

- Each module has a `tests/` subfolder
- Minimum test coverage: all service layer functions
- Use `pytest` + `pytest-asyncio` for async test support
- Use a separate test database (SQLite in-memory or test PostgreSQL schema)
- CI: run tests on every git push before any deployment
